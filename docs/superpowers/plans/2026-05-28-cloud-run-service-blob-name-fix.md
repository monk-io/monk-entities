# cloud-run-service blob_name Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix `gcp/cloud-run-service` `blob_name` source deploy by routing through Cloud Build (matching `gcloud run deploy --source`) instead of the broken Cloud Run v2 API `sourceCode` field.

**Architecture:** When `blob_name` is set, the entity now: (1) uploads source to GCS as a `.tgz`, (2) submits a Cloud Build job using the `gcr.io/buildpacks/builder:v1` buildpack builder to produce a Docker image in Artifact Registry, (3) polls the build to completion, then (4) deploys the Cloud Run service with `container.image = <built URI>` — the same code path as a regular `image:` deploy.

**Tech Stack:** TypeScript, Cloud Build API v1 (`cloudbuild.googleapis.com`), Artifact Registry API, existing `GcpEntity` base class helpers (`this.get`, `this.post`, `waitForOperation`).

---

## Background

### Why the old approach failed

`blob_name` previously set `container.sourceCode.cloudStorageSource` in the Cloud Run v2 API request. This puts source code directly into the service spec without running the Cloud Native Buildpack BUILD phase. At container start, the `/serve` launcher looks for a `plan.toml` generated by that BUILD phase — it never exists, so `npm install` never runs and the container fails with `MODULE_NOT_FOUND`.

`gcloud run deploy --source` takes a different path: it calls the Cloud Build API to run the buildpack BUILD phase, waits for a Docker image to be produced in Artifact Registry, then deploys that image. This plan makes the entity match that behaviour.

### Required GCP APIs

The caller's `enable-apis` entity must include:
- `cloudbuild.googleapis.com`
- `artifactregistry.googleapis.com`

Both are already included in the `gcp-cloudrun-multi-service` example. The entity's README should document this.

```typescript
/**
 * Poll a Cloud Build build until it reaches a terminal state.
 * Build can take 3-10 minutes depending on dependency count.
 */
private waitForCloudBuild(buildId: string): void {
    const buildUrl = `${CLOUD_BUILD_API_URL}/projects/${this.projectId}/builds/${buildId}`;
    const terminalStatuses = ["SUCCESS", "FAILURE", "INTERNAL_ERROR", "TIMEOUT", "CANCELLED"];
    const maxAttempts = 120;  // 20 min at 10s intervals
    const delayMs = 10000;

    for (let i = 0; i < maxAttempts; i++) {
        const resp = this.get(buildUrl);
        const status: string = resp.status || "QUEUED";

        cli.output(`Cloud Build status: ${status} (${i + 1}/${maxAttempts})`);

        if (status === "SUCCESS") return;
        if (terminalStatuses.includes(status)) {
            const logUrl = resp.logUrl || "(no log URL)";
            throw new Error(`Cloud Build ${buildId} failed with status ${status}. Logs: ${logUrl}`);
        }

        // Busy-wait delay (Goja runtime has no setTimeout)
        const start = Date.now();
        while (Date.now() - start < delayMs) { /* spin */ }
    }

    throw new Error(`Cloud Build ${buildId} did not complete within ${maxAttempts * delayMs / 1000}s`);
}
```

```typescript
/**
 * Ensure the `cloud-run-source-deploy` Artifact Registry Docker repository exists.
 * Cloud Run creates this repo automatically on first `gcloud run deploy --source`,
 * but the API path requires it to be pre-created.
 */
private ensureArtifactRegistryRepo(): void {
    const repoId = "cloud-run-source-deploy";
    const repoUrl = `https://artifactregistry.googleapis.com/v1/projects/${this.projectId}/locations/${this.definition.location}/repositories/${repoId}`;

    const check = this.get(repoUrl);
    if (check) return;  // already exists (get returns null on 404)

    cli.output(`Creating Artifact Registry repo: ${repoId}`);
    const createUrl = `https://artifactregistry.googleapis.com/v1/projects/${this.projectId}/locations/${this.definition.location}/repositories?repositoryId=${repoId}`;
    this.post(createUrl, {
        format: "DOCKER",
        description: "Cloud Run source deployments",
    });
    // Repo creation is synchronous in AR API — no LRO needed
}
```

> **Note on `get` returning null:** `GcpEntity.handleResponse` (in `gcp-base.ts`) returns `null` for 404 responses by default. Verify this behaviour in `src/gcp/gcp-base.ts` around `handleResponse` before assuming — adjust the check if needed.

## Task 3: Add `buildImageFromSource` — the Cloud Build orchestration method

**Files:**
- Modify: `src/gcp/cloud-run-service.ts` (new private method)

This method replaces the old `container.sourceCode` approach end-to-end.

---

- [ ] **Step 1: Add the method**

Insert after `ensureArtifactRegistryRepo` in `src/gcp/cloud-run-service.ts`:

```typescript
/**
 * Build a Docker image from source code using Cloud Build + Google Cloud Buildpacks.
 * This replicates the `gcloud run deploy --source` flow:
 *   1. Ensure the Artifact Registry repo exists
 *   2. Submit a Cloud Build job with the uploaded source and buildpack builder
 *   3. Poll until the build succeeds (3-10 min for Node.js apps)
 *   4. Return the image URI (already pushed to AR by Cloud Build)
 */
private buildImageFromSource(sourceRef: { bucket: string; object: string }): string {
    this.ensureArtifactRegistryRepo();

    const imageUri = this.buildImageUri();
    const buildUrl = `${CLOUD_BUILD_API_URL}/projects/${this.projectId}/locations/${this.definition.location}/builds`;

    const buildBody = {
        source: {
            storageSource: {
                bucket: sourceRef.bucket,
                object: sourceRef.object,
            },
        },
        steps: [
            {
                // Google Cloud Buildpacks builder: auto-detects Node.js/Python/Go/Java
                // from package.json / requirements.txt / go.mod / pom.xml respectively.
                // For Node.js: runs `npm install` then sets CMD to `npm start`.
                name: "gcr.io/buildpacks/builder:v1",
            },
        ],
        images: [imageUri],
        options: {
            logging: "CLOUD_LOGGING_ONLY",
        },
    };

    cli.output(`Submitting Cloud Build for source deploy (image: ${imageUri})...`);
    const buildOp = this.post(buildUrl, buildBody);

    // The response is a long-running operation; the build ID is in metadata
    const buildId: string | undefined = buildOp?.metadata?.build?.id;
    if (!buildId) {
        throw new Error(`Cloud Build submission failed — no build ID in response: ${JSON.stringify(buildOp)}`);
    }

    cli.output(`Cloud Build started: ${buildId}`);
    this.waitForCloudBuild(buildId);
    cli.output(`Cloud Build complete — image: ${imageUri}`);

    return imageUri;
}
```

### Known risks

1. **Builder image tag**: `gcr.io/buildpacks/builder:v1` is assumed stable. Verify by checking `gcloud run deploy --source . --log-http 2>&1 | grep buildpacks` on a live project — the tag in the Cloud Build submission is the authoritative answer.

2. **Cloud Build SA permissions**: Cloud Build's default SA (`PROJECT_NUMBER@cloudbuild.gserviceaccount.com`) must have `artifactregistry.writer` on the project. This is granted automatically when `artifactregistry.googleapis.com` is enabled via the service account's default bindings — but if a project has custom IAM, this may need explicit granting. Handle gracefully in the error from Task 7, step 5.

3. **Parallel builds**: When the stack has multiple `blob_name` services (api + frontend), both will submit Cloud Build jobs. Each waits independently in the entity's `create()` lifecycle. This is fine — Cloud Build parallelises them automatically.

4. **`ensureArtifactRegistryRepo` 404 handling**: The plan assumes `GcpEntity.get()` returns `null` for 404. Verify in `src/gcp/gcp-base.ts:handleResponse` — if it throws instead, wrap in a try/catch.
